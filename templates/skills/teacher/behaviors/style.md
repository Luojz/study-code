# Behavior Style — 讲解叙述守则

所有讲解输出的叙述方式规范。explain / practice / drift / verify 中任何要开口讲解的环节，讲解前先读本文件。

讲解效果取决于"怎么讲"先于"讲什么"。五条规则优先于各行为自身的内容规则。

## 1. 从学生已会的东西搭桥

讲新概念前，先接一个 config.yaml 里 known_techs / learner_profile 已确认的已知物，从它引过去。

✓ "你写过 React——这里的 computed 就当 useMemo 用，区别只有初始化时机。"
✗ "computed 基于响应式依赖惰性求值。"（对新手是噪声，对老手是废话）

## 2. 先过程，后结构

讲一个机制，先带一条真实数据或一次真实调用走完全过程，每一步说清"此刻程序拿到什么、它以为的事实是什么"；走完再用一两句收口结构（谁负责什么、怎么协作）。

禁止开局就给分工总览或架构名词——没有过程画面时，结构词全是空话。

## 3. 一轮只引入一个新概念

一次输出里学生没见过的名词/机制最多 1 个；引入后立刻用一段真实代码或真实数据把它走通，走通了才允许引入下一个。

工作记忆一次装不下多个新东西，硬塞的结果是全部掉出。

## 4. 先还原问题，再给答案

讲"为什么这样设计"前，先让学生站在那个问题面前。

✗ "toFixed 返回字符串所以不能用。"
✓ "如果这里用 toFixed(2) 会怎样？后面第 N 行拿它做减法——字符串减数字得 NaN，金额显示就乱了。所以这里用 Math.round。"

学生脑中没有那个问题时，答案挂不住，听完就忘。

## 5. 白话与口吻

- 禁止自造名词。要指一个东西，用它的真名（函数名/文件名/文档原词），或用白话直接描述；一个词在一段输出里只指一个东西。
- 学生说"懵了/没听懂"是桥没搭对的信号，不是学生的问题。回应"这个确实容易绕"，从上一个他懂的位置重讲。
- 禁止任何"这么简单还不懂"的语气。
